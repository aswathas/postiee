Read that table again

Most of it is red. That isn't a gap in the product — it's the reason the product is this shape.

LinkedIn has a permission whose entire job is letting an app read your own posts. It isn't slow. It isn't paid. It is closed — the documentation says it is not accepting access requests at all.

So you can write to LinkedIn through an approved app, but nothing can read back what it wrote. Post something, lose the identifier, and that post is gone. Not hidden. Gone.

That is why postiee captures the identifier the moment a post is created and keeps the record itself. The local history isn't a bonus feature. It's the only copy that will ever exist.

Everything green in that table is inside the self-serve tier. Everything amber or red is either partner-gated or does not exist at any tier. The full breakdown is here.

What it does

Five things. No half-finished commands, no stubs that fail on first use.

post

Write a thought, attach one image, choose who can see it.

history

Every post written to your own database the moment it's made.

search

Find that thing you posted in March without scrolling LinkedIn.

unpublish

Delete a post on LinkedIn itself, then drop it from your history. No undo.

forget

Drop a post from your history and leave it live on LinkedIn.

The three traps

Every one of these breaks a naive LinkedIn client, and all three fail silently.

The post ID arrives in a response header while the body is empty. Person IDs are scoped per app, so yours must be resolved at runtime. And URNs in paths need full percent-encoding, which Go's PathEscape does not do. postiee handles all three, and each has a test. How it works walks through them.

Your agent already knows how

Any agent that can run a shell command can drive it.

There's an --agent flag that switches every command to clean JSON, an MCP server, and an installable skill for Claude, Codex, and Cursor. Point it at whatever you already use and posting stops being a separate chore.
